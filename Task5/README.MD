#### Кейс-задача № 5
- Сформировать и описать аналитический обзор проделанной работы в одной из кейс-задач № 1-4 на Ваш выбор, по следующим критериям:
- Функциональность: Это основной критерий, который оценивает, насколько хорошо программа выполняет свои задачи. Программа должна корректно обрабатывать все входные данные и выдавать правильные результаты.
- Производительность: Этот критерий оценивает скорость работы программы. Быстрая работа программы важна для приложений, где требуется обработка большого объема данных или высокая интерактивность.
- Удобство использования (юзабилити): Критерий, который оценивает, насколько легко пользователь может взаимодействовать с программой. Удобный интерфейс и понятные сообщения об ошибках делают программу более привлекательной для пользователей.
- Безопасность: Важный критерий, особенно для программ, которые работают с конфиденциальными данными. Безопасная программа должна защищать данные от несанкционированного доступа и предотвращать возможные уязвимости.
- Масштабируемость: Критерий, который оценивает, насколько легко программу можно расширить или модифицировать для обработки большего объема данных или добавления новых функций.
- Сопровождаемость: Оценивает, насколько легко поддерживать и обновлять программу. Хорошо структурированный код, четкие комментарии и документация упрощают процесс сопровождения.
- Переносимость: Критерий, который оценивает, насколько легко программу можно перенести на другую платформу или систему без значительных изменений.
- Качество кода: Оценка качества кода включает такие аспекты, как читаемость, структурированность, использование стандартных практик и паттернов проектирования, отсутствие ошибок и т.д.
- Тестирование: Критерий, который оценивает, насколько хорошо программа была протестирована. Полное тестирование помогает выявить ошибки и улучшить качество программы.

#### Ответ
Анализ по задаче № 4 - Web приложение.

##### Функциональность
Приложение реализовано скорее, как MVP, нежели полный продукт. Общая категория приложения - Productivity Tools.
Приложения принадлежащие к данной категории обычно ставят своей задачей расчет и отображение пользователю целого спектра различных метрик, собранных или вычисленных по вводным данным пользователя.
В моем приложении активно используется только временной и категориальный аспекты вводных данных, 
присутствуют реализовано только два способа отображения собранных метрик (список и график).
Кроме того таймстэмп начала и завершения задач генерируется во время записи данных в базу, а значит данные имеют небольшую задержку. 
История по activity отображается только за текущий день, юзер не имеет доступа к своим данным далее, чем за сегодня.

###### Рекоммендации к улучшению функциональности
- Замерять начало и конец activity на фронтенде и передавать эти значения на сервер для записи в базу
- Реализовать логику оценки частоты и регулярности определенных activity юзера, к примеру оценивать вероятность определенных activity в зависимости от дня недели и времени дня, и анализировать динамику таких тенденций (юзер стал чаще/реже делать что-то за какой-то период).
- Расширить на сервере запрос по получению истории activity (получение истории по конкретным дням) и реализовать на клиенте виджет-календарь, позволяющий просматривать метрики/аналитику по доступным прошедшим дням.

##### Производительность
В текущем состоянии относительно ограниченного фкнционала и вполне линейной одномерной логики производительность сервера будет удовлетворительна для небольшого числа пользователей.
В виду того, что серверная часть приложения в данной конфигурации представлена одним процессом, обслуживающим все запросы, предельная производительность ограничена ресурсами этого одного ключевого процесса.
Отдельные хэндлеры HTTP-запросов выполняют по несколько запросов в базу данных, что далеко не является оптимальной практикой. 
БД представлена одним инстансом, что при большой нагрузке превратится в бутылочное горлышко - запросы к бд будут копиться в очередь при предельной нагрузке.
В свою очередь фронтенд-часть приложения написанная на реакте представляет собой довольно быстрый, ненагруженный одностраничный клиент. Его производительность ограничивается только скоростью ответа сервера.

###### Рекоммендации к улучшению производительности
- Для горизонтального скейлинга приложения необходимо настроить балансировщик запросов и реализовать серверную часть как cgi хэндлеры. Альтернативно можно рассмотреть облачное решение, где серверную логику будут выполнять on-demand лямбды.
- Устранить потенциальное бутылочное горлышко в виде единственного инстанса БД. Разделить БД на primary(write) инстансы и hot-реплики для чтения архивных записей в случае большого количества пользователей.
- Рассмотреть postgreSQL на замену MySQL для использования процедур  для переноса многоступенчатых запросов с сервера непосредственно в базу, а также использование view для более эффективной выборки данных из БД.
- Реализовать логику кэширования и снхронизации истории activity на клиентском приложении, позволяющую клиенту быть независимым от серверной части в случае разрыва соединения из больших задержек.

##### Удобство
Одностраничный вариант приложения мне кажется удобным и приятным в контексте UX. Плавные переходы, отсутствие необходимости перезагрузки, также возможность поддержки мобильной браузерной версии приложения через media без необходимости использования standalone приложения.
Однако в приложении не реализованы tips, подсказки и туториалы, которые бы позволили пользователю быстро понять логику пользования. В текущем варианте приходится полагаться только на внимательность и интуицию пользователя.
Отсутствуют возможности экспорта метрик в виде файлов, а также share через мессенджеры и другие платформы.

###### Рекоммендации к улучшению удобства пользования
- Реализовать tips, подсказки
- Добавить tutorial сценарий или превью функциональности
- Добавить возможость экспорта метрик

##### Безопасность
Приложение сохраняет довольно "чувствительные" персональные данные пользователя - при условиях предполагаемого использования инструмента, это почти полное расписание человека в течение дня. 
Хэш пароля юзера сохраняется на данный момент в одну таблицу вместе с самими данными пользователя, что является негативной практикой. Нет никакой обфускации данных юзера (хотя бы засчет разделения хранения). 
В приложении используется сессионная авторизация и ключ сессии используется для авторизации - также небезопасная практика.
В приложении не реализовано подтверждение уникальности пользователя через email или телефон.
Не реализован механизм восстановления аккаунта, пароля.

###### Рекоммендации к улучшению безопасности
- Шифрование хранимых данных пользователя и/или использование обфускации чувствительных данных пользователя
- Использование короткоживущих, экспирируемых JWT токенов для аутентификации вместо сессионной аутентификации
- Реализовать механизм восстановления аккаунта, пароля
- Реализовать подтверждение уникальность пользователя через email, телефон, смс

##### Сопровождаемость
Большая часть нюансов и замечаний по качеству сопровождаемости приложения относится к серверной части. 
Данное мнение субъективно. Серверное приложение реализованное во фреймворке Delphi может быть удобным с точки зрения доступности "out of the box" для быстрого старта, однако доступность специалистов имеющих регулярный и актуальный опыт разработки в Delphi намного ниже чем специалистов по разработке web серверов на Python, C++, node JS и т.д. Кроме того Delphi является лицензированным ПО, что является наиболее неудобным и ограничивающим нюансом с легальной точки зрения и финансовой.
Что касается реализации данного (моего) приложения, код вполне можно оценить как удобно-читаемый и неперегруженный, правда надо сказать что большая часть кода относится к парсингу вводных данных из запросов, сетевой логике в приципе и выполнению запросов в базу (что не является сложной вычислительной логикой).
Клиентская часть написанная на TypeScript может показаться неоптимальной и неудобной из-за отсутствия консистентности в нэйминге паременных, коллбэков и логике виджетов. TypeScript как более или менее популярный ЯП можно считать удобным к разработке и сопровождению.
Подробная документация как к серверному, так и к клиентскому приложению на данный момент отсутствует.

###### Рекоммендации к улучшению сопровождаемости
- В случае принятия данного приложения в рамках MVP стороной заказчика, рекомендуется провести полную декомпозицию для удобства описания ТЗ и архитектуры серверного и клиентского приложения.
- В случае испольования MVP как альфа версии приложения, необходимо провести хотя бы один прозод рефакторинга и опционально оставить комментарии в сомнительных "местах" для референса в последующих циклах разработки
- Создать сопровождающую документацию к серверному и клиентскому приложениям

##### Переносимость
Серверная часть реализованная на Delphi может быть без больших временных и ресурсных затрат адаптирована под unix-based системы, благодаря кроссплатформенности Delphi фреймворка.
Клиентская часть может быть адаптирована в десктопное приложение с использованием электрона, однако для создания мобильного приложения придется искать альтернативные решения, если понадобится что-то чуть большее, чем браузерная мобильная версия.
Переносимость оптимистичная и высокая с серверной стороны, более низкая с клиентской стороны (в случае необходимости реализации мобильного приложения).

##### Тестирование
Данное приложение прошло только ручное тестирование со стороны браузерного клиента и ручное тестирование API с помощью постмана. По сути был проведен только общий smoke тест. 
Для данного приложения отсутствуют unit-тесты, тесты БД, интеграционные тесты.

###### Рекоммендации к улучшению тестирования
- Реализовать unit-тесты для серверного и клиентского приложений
- Реализовать тесты БД
- Реализовать сквозные и интергационные тесты функционала
