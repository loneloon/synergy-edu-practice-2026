#### Кейс-задача № 3
Спроектируйте базу данных «Туризм» (перечень предоставляемых услуг, заказ туров и др.). При проектировании базы данных необходимо создать 4-5 таблиц предметной области: 3-4 таблицы-справочника и 1 таблицу переменной информации. Для всех таблиц создать первичные ключи. Построить связи между таблицами при помощи внешних ключей: атрибуты таблицы переменной информации должны ссылаться на ключевые атрибуты таблиц справочников. 
#### Ответ
files: ./setup_db.sql ./install_schema.sql ./fill_db.sql

#### Деплой
Выполнить скрипты в следующей последовательности
- 1. Подключение к серверу
- 2. setup_db.sql для создания БД
- 3. install_schema.sql для создания таблиц (без указания схемы, т.е. таблицы будут расположены на схеме public)
- 4. fill_db.sql для заполнения БД тестовыми данными

#### Комментарий
Для задачи смоделирeм базу данных 'tourism'. Условие позволяет нам выбрать собственные таблицы.
В качестве главных таблиц переменной информации реализуем таблицы для хранения записей об отелях и турах, назовем их hotel и tour соответственно.
Подберем выгодные поля/колонки для вышеупомянутых таблиц.
Для таблицы hotel нам подойдут колонки содержащие основную информацию - имя и описание, данные о местоположении отеля - адрес, город, страна, и наконец - рейтинг отеля и стартовая цена за ночь.
Для таблицы tour аналогично с отелем подойдут имя и описание, рейтинг и цена за тур, а также для обозначения общего месторасположения тура используем город и страну.
Черновики таблиц отель и тур выглядят для нас следующим образом:
hotel (Отель):
    - имя/название
    - описание
    - адрес
    - город
    - страна
    - рейтинг
    - цена
tour (Тур):
    - название
    - описание
    - рейтинг
    - цена
    - город 
    - страна

Оценим первичные модели и подумаем о нормализации и дедубликации данных. С первого взгляда сразу понятно, что размещать в таблицы два поля город и страна - это bloat.
Можно заранее запланировать таблицу справочник city (город), в которой каждый горд будет ссылаться на соответствующую ему страну в другой таблице-справочнике country (страна). Таким образом из двух колонок (город и страна) мы можем оставить в таблицах отель и тур колонку город, которая будет по внешнему ключу ссылаться на соответствующую таблицу, и мы всегда сможем получить достаточную информацию о местоположении, выполнив JOIN при выборке.
Таким образом получаем две новые таблицы город и страна и уточнение моделей город и отель.
Воспользуемся возможностью распланировать хранение информации специфичной для отдельных стран и полезной в выбранной предметной области - туризм:
С отдельной записью о стране мы можем ассоциировать валюту страны, также основной язык страны и, к примеру, индекс безопасности страны.
Отдельные языки и валюты могут ассоциироваться с несколькими странами, соответственно в целях дедубликации данных вынесем их в отдельные таблицы: language и currency.
Таким образом на данном этапе мы имеем следующие таблицы:
- language: название языка страны
- currency: местная валюта
- country: страна
- city: город страны
- hotel: отель
- tour: отдельный тур/туристическая программа

Перечислим выбранные колонки для наших таблиц:
- language (Язык):
    - name: название
- currency (Валюта):
    - name: название
- country (Страна):
    - name: название
    - currency: fk
    - language: fk
    - safety_index: индекс безопасности страны
- city (Город):
    - name: название
    - country: fk
- hotel (Отель):
    - name: название
    - price: мин. стоимость за ночь
    - rating: рейтинг
    - description: описание
    - address: адрес
    - city: fk
- tour (Тур):
    - name: название
    - price: стоимость
    - rating: рейтинг
    - description: описание
    - city: fk

Для удобства заполнения и референсов между таблицами во всех таблицах в качестве первичного ключа будем использовать колонку id с большим целочисленным ключом, который будет заполняться как автоинкремент (+1 к каждой новой записи) по дефолту. 
Далее подберем для колонок таблиц подходящие типы.
Распределим запросы по стадиям установки БД - разместим создание базы в отдельном скрипте setup_db.sql, чтобы дать себе возможность при необходимости настроить БД перед созданием таблиц в будущем, создание самих таблиц в скрипте install_schema.sql и наконец вставку тестовых/первоначальных данных в скрипте fill_db.sql

Дополнительно оценим "нормальность" созданной БД.
БД может считаться нормализованной (2NF-3NF), т.к.:
- данные хранятся в атомарном виде
- отсутствуют дублированные данные: повторяющиеся значения реализованы в сложных таблицах, как референсы по внешнему ключу
- нет повторяющихся групп
- отсутствуют транзитивные зависимости
